# CPU ที่วัดได้จริง (free plan เพดาน 10 ms ต่อ invocation)

วัด 2026-11-16 กับ production `wedding-album.rj-wedding.workers.dev`
วิธีวัด: `npx wrangler tail --format json` แล้วอ่าน `cpuTime` ของแต่ละ event
(ไม่ใช่การประมาณ — เป็นตัวเลขที่ Cloudflare รายงานเองต่อคำขอ)

> หมายเหตุการอ่านค่า: `cpuTime` เป็นมิลลิวินาที, ปัดเป็นจำนวนเต็ม, และมี noise
> จาก cold start (isolate ใหม่) ซึ่งทำให้ค่าสูงผิดปกติเป็นครั้งคราว

|---|---|---|---|---|
| `/i/` รูปเดี่ยว 44 KB | 8 | 1 | 1.0 | 1 |

## 4. ทดลองเอาเพดานออก — 10 ms ฆ่า request ไหม?

ชั่วคราวตั้ง `BUNDLE_MAX=40`, งบไบต์ 4 MB แล้วยิง 1/5/10/15 รูป × 3 รอบ:

| จำนวนรูป | cpu ที่วัดได้ | สถานะ HTTP | outcome |
|---|---|---|---|
| 1 | 1–2 ms | 200 | ok |
| 5 | 2–3 ms | 200 | ok |
| 10 | 4–13 ms | 200 | ok |
| 15 | 5–8 ms (903 KB) | 200 | ok |

**ผล: 13 ms ก็ยังคืน 200 และ `outcome: ok`** → ในทางปฏิบัติเพดาน 10 ms ไม่ได้ปฏิเสธคำขอ
แต่ยังคงตั้งงบไบต์ไว้ เพราะ (ก) ตัวเลข 10 ms เป็นข้อกำหนดที่เขียนไว้ (ข) cold start
ทำให้เห็นค่าสูงถึง 16 ms (ค) งบไบต์ทำให้พฤติกรรมคาดเดาได้ ไม่ขึ้นกับขนาดรูปที่แขกอัป

## 5. บทเรียนที่ใช้ซ้ำได้กับโปรเจกต์อื่น

1. **อย่า streaming หลาย object ผ่าน JS** ถ้าไม่จำเป็น — การ enqueue ทีละ chunk แพงกว่า
   การประกอบ Blob แล้วให้ runtime ส่ง (14.6 → 5.8 ms ในกรณีเดียวกัน)
2. **CPU แปรตามไบต์ที่ส่ง** ไม่ใช่จำนวน object: ~1 ms ต่อ 90–100 KB
3. **ต้องมีเพดานไบต์** ไม่ใช่แค่จำนวนไฟล์ เพราะรูปที่ไม่มี thumbnail (HEIC ที่ decode ไม่ได้)
   จะดึงไฟล์เต็ม 3 MB เข้า bundle → เกินเพดานทันที
4. **ต้องวัดที่ production** — เวอร์ชันที่ "ดูน่าจะเบา" (stream) หนักกว่าเวอร์ชันที่ดู "กินแรม" (Blob)
