## 1. โมเดลที่ใช้คิด (ต้องเข้าใจก่อนเลือกทาง)

```
requests/วัน = (คำขอที่ "เข้า Worker script") × จำนวนครั้ง
```

| นับ | ไม่นับ |
|---|---|
| `/api/*`, `/i/*`, cron trigger, HEAD/OPTIONS ที่เข้า Worker | static assets (`/`, `/app.js`, `/styles.css`, `/art/*`) — **ฟรีไม่จำกัด** |
| (แยกเป็น R2 Class A/B ไม่ใช่ Worker request) | subrequest ที่ Worker ยิงออกไป (R2 binding, fetch) |

**cache ไม่ช่วยลด request** — Cloudflare ระบุชัดว่า Workers รันก่อน cache และ "Workers Caching"
เมื่อเปิดใช้ก็ยัง **คิดเงินเท่ากับ request ที่เข้า Worker** ทุกครั้ง
(ที่มา: pricing หมายเหตุ 4 + Fine Print) → ทางเดียวที่จะตัด request คือ **ไม่ให้คำขอนั้นเข้า Worker เลย**

**static assets ใช้เก็บรูปแขกไม่ได้** 2 เหตุผล:
1. รูปเกิดหลัง deploy — asset ต้องอยู่ในชุด deploy
2. static assets **ไม่รองรับ Range** (คืน 200 พร้อมไฟล์เต็ม ไม่มี `Content-Range`) → วิดีโอบน Safari/iPhone เล่นไม่ได้

## 3. ทาง A — จ่ายเงิน (ตัดปัญหาทั้งหมด)

### A1. Workers Paid $5/เดือน ← ถูกที่สุดและเสี่ยงน้อยที่สุด

| หัวข้อ | รายละเอียด |
|---|---|
| ได้อะไร | ไม่มีเพดานรายวัน · 10M requests/เดือนรวม (พอ 4 เท่า) · CPU 10 ms → 30 วินาที · subrequest 50 → 1,000 |
| ค่าใช้จ่าย | **$5 (~180 บาท) 1 เดือน** แล้ว downgrade กลับฟรีหลัง 22 ธ.ค. |
| งานโค้ด | **0 บรรทัด** — เปลี่ยนแผนใน dashboard |
| Trade-off | เสียเงิน 180 บาท · ต้องผูกบัตร (มีอยู่แล้ว) · ต้องจำ downgrade |
| กันค่าใช้จ่ายบาน | ตั้ง **spending limit** (ฟีเจอร์ 2026) เช่น $6 → เกินแล้วหยุด invocation เอง |
| หมายเหตุ | ค่า R2 ยังคิดแยก (~5.6 บาท/เดือน จากพื้นที่เกิน 10 GB) |

**ทำไม CPU 30 วินาทีสำคัญ**: ZIP ทั้งอัลบั้ม (13,000 รูป) และ `/api/sync` ไป Drive จะไม่ชน 10 ms อีก

### A2. ซื้อโดเมน + ผูก R2 custom domain

| หัวข้อ | รายละเอียด |
|---|---|
| ได้อะไร | รูป/วิดีโอเสิร์ฟตรงจาก R2 → **ไม่กิน Worker request เลย** · ได้ CDN cache (Smart Tiered Cache) · WAF / Bot Management · URL สวยให้แขก (`photos.xxx.com`) |
| ผลกับโควตา | วันงานเหลือ **~28,500 (29%)** เพราะเหลือแค่ config + list + อัปโหลด |
| ค่าใช้จ่าย | โดเมน ~350–450 บาท/ปี (`ESTIMATE`) + 0 ค่า R2 |
| งานโค้ด | **0** — `wrangler.toml` มี `PUBLIC_MEDIA_BASE` รออยู่แล้ว ใส่ค่าแล้ว deploy |
| เงื่อนไข | zone ต้องอยู่ใน **account เดียวกับ bucket** · ถ้าโดเมนอยู่ที่อื่นต้องใช้ partial (CNAME) setup ซึ่ง **Business plan ขึ้นไปเท่านั้น** |
| Trade-off | ต้องมี/ซื้อโดเมน (ช้า 1–24 ชม. กว่า DNS จะติด) · ยังต้องดูแลอัลบั้มให้ไม่หลุดโควตาฝั่ง API (แต่เหลือน้อยมาก) |

### A3. Cloudflare Images — **ไม่แนะนำสำหรับงานนี้**
ฟรี 5,000 transformation/เดือน แต่ตัวเก็บรูปคิดเงิน และไม่ได้แก้อะไรที่เราต้องการ (ปัญหาเราคือ request ไม่ใช่การแปลงรูป)

## 4. ทาง B — ฟรี แต่ต้องแก้โค้ด/สถาปัตยกรรม

### B1. Presigned URL ให้รูปวิ่งตรงจาก R2 (`r2.cloudflarestorage.com`) — **ฟรี ไม่ต้องมีโดเมน**

`GET` presigned URL ใช้ได้กับ S3 API domain, อายุ 1 วินาที – 7 วัน, ลงนามใน Worker ด้วย `aws4fetch`

| หัวข้อ | รายละเอียด |
|---|---|
| ผลกับโควตา | เท่ากับ A2: วันงานเหลือ **~28,500 (29%)** — รูป/คลิปไม่เข้า Worker |
| งานโค้ด | ~3–4 ชม.: `aws4fetch` + เก็บ R2 access key เป็น secret · `mediaUrl()` คืน presigned URL · ตั้ง CORS ของ bucket ให้ origin ของเรา |
| Trade-off 1 | **ไม่มี CDN cache** → ทุกครั้งที่ดูคืออ่าน R2 จริง (Class B ฟรี 10M/เดือน — เราใช้ ~1% ของนั้น) latency สูงกว่า cache เล็กน้อย |
| Trade-off 2 | URL ยาว ~250 ตัวอักษร × 15 รูป → list response โตขึ้น ~4 KB (ยอมรับได้) |
| Trade-off 3 | URL เปลี่ยนทุกครั้งที่เซ็นใหม่ → browser cache พลาด · แก้ได้ด้วยการปัดเวลาเซ็นให้ตรงชั่วโมง (URL นิ่งในช่วงนั้น) |
| Trade-off 4 | อายุไม่เกิน 7 วัน → ต้องเซ็นใหม่ทุกครั้งที่โหลด list (ทำอยู่แล้ว) |
| Trade-off 5 | เปิดเผย account id + ชื่อ bucket ใน URL · presigned = bearer token ใครมีลิงก์ก็ดูได้ (อัลบั้มเราก็ public อยู่แล้ว) |
| Trade-off 6 | ใช้กับ custom domain **ไม่ได้** (R2 ระบุชัด) — เลือกทางใดทางหนึ่ง |

### B2. อัปโหลดเป็นชุด (batch upload) — ลดครึ่งที่ใหญ่ที่สุดของวันงาน

รวม 15 รูปเป็น multipart 1 request แทน 15 × 2

| หัวข้อ | รายละเอียด |
|---|---|
| ผลกับโควตา | อัปโหลด 27,200 → **~2,000** · รวมวันงานเหลือ **~32,550 (33%)** |
| งานโค้ด | ~4–6 ชม.: ฝั่ง client รวม FormData + ความคืบหน้ารวม · ฝั่ง Worker แยกส่วนและเขียน R2 ทีละไฟล์ |
| Trade-off 1 | **เสีย per-file retry** — พลาดไฟล์เดียวต้องส่งชุดใหม่ หรือแบ่งชุดย่อย |
| Trade-off 2 | บน plan ฟรี CPU 10 ms ต่อ invocation อาจไม่พอ parse 10 MB (บน Paid 30 วินาที ไม่มีปัญหา) |
| Trade-off 3 | แถบความคืบหน้าเป็นรายชุด ไม่ใช่รายไฟล์ · ต้องแก้ UI ที่เพิ่งทำเสร็จ |

### B3. Bundle read — 1 request คืนหลายรูปย่อ ✅ **ทำแล้ว (2026-11-16)**

| หัวข้อ | ระบุ |
|---|---|
| สถานะ | **ใช้งานจริงแล้ว** — `GET /api/page?e=CODE&k=<keys>` (สูงสุด 8 รูป/คำขอ, งบไบต์ 420 KB) |
| ผลที่วัดได้ | หน้า 15 รูป = **1 list + 3 bundles = 4 requests** (เดิม 15) · รูปทุกใบมาทาง bundle (0 individual) |
| เปิดอัลบั้มครั้งแรก | **5 requests** (config 1 + list 1 + bundle 3) เดิม 17 |
| เปิดซ้ำ | **1 request** (list เท่านั้น; bundle อยู่ใน cache 1 ปี) เดิม 10 |
| CPU ที่วัดได้ | median 4 ms, avg 5.6, p90 8 (`wrangler tail`) — ไม่ชนเพดาน 10 ms |
| Trade-off | รูปแรกมาช้ากว่าเดิม (รอทั้งก้อน 397–420 KB) · ถ้า bundle ล้ม client ถอยไปยิงรายรูปเองอัตโนมัติ (หลังล้ม 2 ครั้ง) · วิดีโอยังแยก request (Range) |

**ทดลองที่สำคัญ**: ถอดเพดาน CPU ออกแล้วยิงถึง 13 ms — Cloudflare ยังคืน **200 / outcome ok**
เพดาน 10 ms จึงไม่ใช่กำแพงที่ฆ่า request ในทางปฏิบัติ แต่ยังคงงบไบต์ไว้ เพราะตัวเลขที่เขียนไว้คือ 10 ms
และ cold start วัดได้ถึง 16 ms (ดู `docs/CPU-MEASUREMENTS.md`)

**วัดจริง 2026-11-16** (`scripts/req_count.mjs`, Chromium 390×844):

| การกระทำ | ก่อน | หลัง |
|---|---|---|
| เปิดหน้า (config) | 1–2 | **1** |
| แตะ "ภาพความทรงจำ" (15 รูป) | 15 | **4** |
| เปิดซ้ำในไม่กี่วินาที | 0–10 | **1** |

→ ตัวเลข "17" คือ `2 + 15` และเป็น **ครั้งแรกของแต่ละเครื่องเท่านั้น**
หลังแก้ `/api/*` ส่ง `cache-control` ชัดเจนแล้ว (ก่อนหน้านี้ browser เดาเอง = เห็นรูปเก่าค้างได้)

### B4. ลดขนาดหน้าจาก 15 → 8 รูป

เปิดอัลบั้ม 17 → 10 requests · ลดได้แค่ ~7% · **แลกกับ UX แย่ลงชัดเจน** (กดดูเพิ่มบ่อยขึ้น) — ไม่คุ้ม

### B5. Service worker + IndexedDB cache ฝั่งแขก

เปิดซ้ำ = 0 request · ช่วย**สัปดาห์หลังงาน** (แขกเข้ามาดูซ้ำ) ไม่ช่วยครั้งแรก · ~3 ชม. · เสี่ยง stale ถ้าเจ้าภาพลบรูป

### B6. ตัวกรอง "รูปของฉัน"

แขกเห็นรูปที่ตัวเองอัปโหลดก่อน (เก็บ id ใน localStorage) → โหลด list/หน้าถัดไปน้อยลง · ~2 ชม. · ผลขึ้นกับพฤติกรรมจริง (ยังไม่รู้)

## 6. คำแนะนำ (เรียงตามความคุ้ม)

1. **ทำ A1: Workers Paid 1 เดือน** — 180 บาทแลกกับการไม่ต้องแตะโค้ดเลย 5 วันก่อนงาน และได้ CPU 30 วินาที (แก้เรื่อง ZIP ทั้งอัลบั้ม + cron sync ที่ค้างอยู่) · ตั้ง spending limit $6 กันบาน · downgrade หลัง 22 ธ.ค.
2. ถ้าไม่อยากจ่ายเลย: **B1 (presigned)** เป็นทางฟรีที่แรงที่สุด (29%) และไม่ต้องมีโดเมน — แต่ต้องทดสอบกับโหลดจริงก่อน
3. ถ้าอยากได้ทั้ง URL สวยและโควตาต่ำถาวร: **A2** (โดเมน) — โค้ดรองรับอยู่แล้ว (`PUBLIC_MEDIA_BASE`) แต่ต้องรอ DNS
4. **A3 (r2.dev) ใช้เป็น plan B ฉุกเฉินเท่านั้น** — เอกสารเขียนว่า rate-limited และห้าม CNAME ไปหา; ถ้าจะใช้ต้องซ้อมยิงโหลดก่อนงาน
5. **B4/B5/B6 ไม่คุ้มจะทำตอนนี้** — ผลน้อยหรือไม่ตรงจุด (ครั้งแรกของแต่ละเครื่องยังนับอยู่ดี)

> ถ้าเลือก A1 ไม่ต้องทำอะไรในโค้ดเพิ่ม แต่ควรทำ 2 อย่างที่ไม่เกี่ยวกับโควตา:
> (ก) แก้ ZIP "ทั้งหมด" ให้ดึงทั้งอัลบั้ม (ค้างอยู่) (ข) ใส่ข้อความสำรองเมื่อ API ตอบ error เพื่อให้แขกเข้าใจว่า "รอ 07:00 น."

## 7. สิ่งที่ยังไม่ได้ยืนยัน (ต้องทดสอบก่อนเลือก B1/A2)
