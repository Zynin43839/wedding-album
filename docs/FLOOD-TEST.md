# Flood test — 600 รูป + 600 คลิป พร้อมกัน (2026-11-16)

ทดสอบจริงบน Cloudflare (`wedding-album.rj-wedding.workers.dev`) ไม่ใช่ localhost
เครื่องทดสอบ: 1 เครื่อง ผ่านอินเทอร์เน็ตบ้าน → edge สิงคโปร์ → Worker → R2

## ชุดที่ 1 — 1,200 ไฟล์ / 2,400 requests @ concurrency 200

| ตัวชี้วัด | ค่า |
|---|---|
| รูป | 600 ไฟล์ × 850 KB (จำลองภาพที่ย่อจากมือถือแล้ว) + thumb 45 KB |
| คลิป | 600 ไฟล์ × 1.0 MB (จำลอง) + poster 45 KB |
| requests | **2,400** |
| ปริมาณข้อมูล | ~1.1 GB |
| เวลารวม | **520.8 วินาที** (8.7 นาที) |
| สำเร็จ | **2,213 / 2,400 (92.2%)** |
| ล้มเหลว | **187 — status 0 ทั้งหมด (ฝั่ง client)** |
| **5xx / 429 จาก Cloudflare** | **0 ครั้ง** |
| latency | p50 **18.0 s**, p95 **96.2 s**, max 244.7 s |
| throughput | 4.2 req/s (~3.5 MB/s — เท่าเพดาน upload ของเน็ตบ้าน) |

**ข้อผิดพลาดที่เกิดขึ้น (ทั้งหมดเป็นฝั่งเครื่องทดสอบ)**

| จำนวน | อาการ |
|---|---|
| 85 | `EOF occurred in violation of protocol` |
| 60 | `TimeoutError` (อ่านไม่ทัน) |
| 20 | `handshake operation timed out` |
| 15 | `RemoteDisconnected` |
| 7 | `WinError 10054` connection reset |

→ 200 connection พร้อมกันจากบ้านหลังเดียวทำให้ NAT/OS ตัดการเชื่อมต่อ ไม่ใช่ Cloudflare ปฏิเสธ

## ชุดที่ 2 — 300 ไฟล์ / 600 requests @ concurrency 30 (สมจริงกว่า)

| ตัวชี้วัด | ค่า |
|---|---|
| สำเร็จ | **600 / 600 (100%)** |
| ล้มเหลว | **0** |
| latency | p50 **4.1 s**, p95 **7.5 s**, max 18.4 s |
| throughput | 6.5 req/s |
| เวลารวม | 92 วินาที |

**สรุปสำคัญ**: ที่ concurrency 30 ไม่มี error เลย และเร็วกว่า (6.5 vs 4.2 req/s) — ยิ่งยิงแรงเกิน เน็ตต้นทางยิ่งช้า

## ความถูกต้องของข้อมูล

| ครั้ง | รายการที่คาด | รายการในอัลบั้ม | ผล |
|---|---|---|---|
| หลังชุด 1 | 1,208 | 1,125 | **ขาด 75** |
| หลังชุด 2 | 1,508 | 1,425 | ตรง (เพิ่ม 300) |

75 รายการที่ขาด = id ที่ไฟล์หลัก (photo/video) ส่งไม่สำเร็จ แต่ thumb/poster สำเร็จ → เข้าเงื่อนไข "ไม่มีไฟล์หลัก" จึงไม่แสดง
**ในแอปจริงไม่เกิดถาวร** เพราะคิวมี retry 3 ครั้ง + ปุ่ม "ลองใหม่ทั้งหมด"; ชุดทดสอบนี้ยิงครั้งเดียวไม่ลองใหม่

## การอ่านอัลบั้ม 1,425 รายการ

| ตัวชี้วัด | ค่า |
|---|---|
| จำนวนหน้า | **17 หน้า** (หน้าละ 180 object) |
| เวลาอ่านทั้งหมด | **7.9 วินาที** |
| รายการครบ | ใช่ ไม่มีซ้ำ ไม่มีหลุด |

→ pagination ทำงานถูกที่ขนาดข้อมูลจริงระดับพันรายการ

## พื้นที่ที่ใช้จริง

อัลบั้มรวม 1,425 รายการ = **1.90 GB** (จาก 1,208 ไฟล์ทดสอบ + 8 ภาพตัวอย่าง)
 extrapolate: 600 คลิปจริง 19 MB = 11.4 GB → เกินฟรี 10 GB แน่นอน (ดู `docs/CAPACITY-650.md`)

## คำตอบ: "ถ้า 600 คนอัปพร้อมกันจะมีปัญหาอะไร"

| ความเสี่ยง | ผลทดสอบ | หมายเหตุ |
|---|---|---|
| Cloudflare ปฏิเสธ/จำกัด rate | **ไม่พบ** (0 × 429/5xx ใน 3,000 requests) | ไม่มี rate limit ฝั่ง Cloudflare โดยค่าเริ่มต้น |
| Worker/R2 รับไม่ไหว | **ไม่พบ** | R2 เขียนได้ตลอด ไม่มี error |
| เน็ตต้นทางเป็นคอขวด | **พบ** — throughput 4-6 req/s จากบ้านหลังเดียว | แขกจริง 650 คนกระจาย 650 เน็ต → ไม่ใช่คอขวดเดียวกัน |
| ไฟล์หลุดเพราะไม่มี retry | **พบ 75 รายการ** | แอปมี retry 3× + ปุ่มลองใหม่ |
| พื้นที่เกิน 10 GB | **จะเกิด** ถ้าคลิปจริง 600 ไฟล์ | ต้องอัปเกรด R2 (~7 บาท/เดือน) |
| โควตา 100k request/วัน | 3,000 requests ที่ทดสอบ = 3% | ปัญหาจริงคือ "การเปิดดู" ไม่ใช่การอัปโหลด |
